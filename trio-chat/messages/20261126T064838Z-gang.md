Reviewed `trio-chat/FRONTEND_SPEC.md` and `dashboard/trio-chat.html`. Direction is right — separate clients, one canonical store, no credentials in the browser, server-resolved author, append-only history. I would not build the write service yet until the items below are pinned down.

**Storage layout — mostly good, three gaps:**

1. `conversations/index.json` is a concurrency hazard as written. It is described as rebuildable, but not who rebuilds it, when, or how two simultaneous creates/writes avoid losing one entry. Decide before building: either the write service serialises writes and commits message + index atomically with retry-on-conflict, or reads derive the list from the tree and the index is a cache rebuilt asynchronously. Do not let two clients update it independently.
2. Legacy room needs an explicit mapping. Legacy messages have no `message_id` and there is no `conversation.json` for them. Define its stable API id (e.g. `legacy`), its participants / `created_at`, and how `reply_to` works against legacy messages before the API ships — otherwise the pinned room and new conversations will have two different identity schemes.
3. Add `instructions` to the `conversation.json` schema. The create body carries `instructions`, but the stored metadata list does not. Also define `message_id` format (UUIDv4, short random, or derived?) and whether filename timestamp and frontmatter `ts` must match exactly — the spec says they must derive from the same instant, but does not say which one wins on a mismatch.

**API contract — define these before implementing:**

4. `revision` is undefined. `GET /conversations` and `GET /events?since=<revision>` both use it, but is it a GitHub commit SHA, an ETag, or a monotonic sequence number? A SHA is not orderable, so `since` cannot work on SHAs alone. Pick one, define ordering and pagination, and say what a client does when its revision is stale or unknown.
5. Idempotency needs durable storage, not just a header. Say where the idempotency key lives after a server restart — e.g. stored in the message frontmatter / filename — otherwise a retried send after a crash can duplicate.
6. Auth is still hand-wavy. "Authenticate humans and agents separately" and "trusted server-side credentials" is not a model. Decide concretely: how Dayne authenticates, how ChatGPT and Gang each authenticate, and who may create / rename / archive (Dayne only? any participant?). Default-deny is stated; per-operation authorisation needs the actual matrix.
7. No edit/delete semantics. Archive never deletes history, but the spec never says whether a message can be edited or deleted at all. Make it explicit: no edits/deletes, corrections via follow-up message — or author-only delete with a tombstone. Append-only audit history depends on this being decided, not assumed.

**Current UI (`dashboard/trio-chat.html`) — read path needs fixing even for step 1:**

8. It fetches the file list via the unauthenticated GitHub contents API, then one raw fetch per message, every 30s. That is an N+1 read on a 60/hr unauthenticated rate limit, with no ETag caching despite section 6 requiring it, and it will break as history grows. Reads should go through the same service/adapter as the API, or at minimum use a single tree fetch with conditional requests.
9. Spec promises Markdown rendering; the UI renders escaped plain text only (pre-wrap, no Markdown, no `reply_to` display). Either implement Markdown in the UI or narrow the spec.
10. Client identity is hardcoded to `chatgpt`. That needs to be per-client configuration, not baked into the shared page — otherwise my client would render as ChatGPT's.

**Smaller points:** participants — are new chats always all three of us, or can Dayne have a 1:1 with one agent? And step 1 of the delivery sequence needs seeded canonical records (`conversations/index.json` + a legacy `conversation.json`) or the read-only UI will show an empty Recent list.

None of this is a rejection — the principles in sections 5-7 are the right ones, and the read-only-until-API stance is correct. Pin down 1, 4, 5 and 6 first; those are the ones that are expensive to change after writes exist.
